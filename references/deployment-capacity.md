# 部署硬件与容量评估

适用：首次部署、选择服务器、增加本地模型/转写/向量库、并发或数据量明显增长、排查资源不足。目标是回答“当前负载能不能稳定运行、需要多少资源、何时扩容、如何证明”，不是自动购买硬件或创建云资源。

## 1. 先确认实际运行边界

把组件列成表：网页/后端、数据库、队列与 worker、图片/音频处理、检索索引、模型推理、备份。记录所在机器/服务和是否与其他项目共享资源。

- 云端 API 模式：模型推理在服务商运行，不把远端大模型的显存算到应用服务器；应用侧仍需评估 CPU、RAM、磁盘、带宽、文件处理和 API 限额。
- 本地模型模式：额外核对模型权重、上下文、并发、GPU/显存、推理引擎及驱动兼容性。小模型可能适合 CPU，不能一概要求独显。
- 混合模式：逐组件区分，例如本地转写/向量化、远端生成，分别估算，避免遗漏或重复计费。
- 已有服务器先检查可用容量与现有服务占用。没有目标主机访问权限时给出假设方案及只读检查清单，不能声称已实测，也不从历史 SSH 信息擅自连接生产。

术语：RAM 是系统内存；VRAM 是显卡显存；vCPU 是云主机分配的计算资源，不等于独占物理核心；worker 是执行后台任务的进程；容量规划是根据负载估算所需资源。

## 2. 收集决定配置的最小输入

先从代码、任务配置、文件大小和已有监控获取，只有影响结论的缺项才问用户。拿不到时给低/中/高负载假设，不能把假设写成现有业务数据。

| 输入 | 说明 |
|---|---|
| 活跃用户与高峰操作 | 注册人数不等于并发请求；记录上传、查询、生成各自峰值 |
| 任务量与时限 | 每日录音总分钟数、每次分析时长、夜间窗口、允许积压时间 |
| 模型路径与配额 | 本地/远端、模型版本、输入输出长度、请求/令牌/并发限额 |
| 数据与保留策略 | 当前数据库、原图、音频体积，每日新增、保留天数、备份份数 |
| 服务目标 | 可接受等待时间、错误率、恢复时间、可容忍数据损失 |
| 增长与预算 | 预计使用周期、增长场景、月预算；价格需要注明地区/币种/日期 |

不要自动把任务处理时限或服务目标填成一个固定数。用户未提供时标“暂定目标，待确认”，仍可先做范围估算。

## 3. 按组件估算资源

### CPU 和 RAM

CPU 核数来自请求处理、文件解码/转码、数据库索引、后台任务等代表性负载测试；不能按用户人数直接换算核数。

RAM 预算包括：系统与基础服务 + 应用/数据库常驻 + 并行任务的增量峰值 + 缓存/索引 + 构建或迁移峰值 + 明确说明的余量。多进程可能重复加载模型与缓存；区分共享、独占和可回收缓存，避免简单相加 RSS 重复计数。

标明配置属于“可启动的开发环境”“在约定负载下的生产候选”“增长/高可用方案”。程序能启动不代表满足生产时限；未实测的生产配置始终是候选。

### 磁盘、对象存储与备份

统一 GB/GiB、分钟/秒单位。用实际文件样本估算日增长，不凭录音条数猜文件大小。

容量组成：已有数据 + 保留期内净新增数据 + 数据库/索引 + 日志 + 临时文件/转换副本 + 发布构建/模型缓存 + 本机备份 + 运维余量。注明新增数据是否已含原件与副本，避免重复计算。

音频粗估字节数 = 总秒数 × 总码率(bit/s) ÷ 8；总码率已含声道时不能再次乘声道。实际编码、头信息与转码副本需用样本修正。

数据库关注读写延迟、并发写入、锁等待、索引和磁盘 IO，而不仅是总空间。SQLite 写锁或慢查询不一定靠加 CPU 能解决。

对象存储、独立备份与本机磁盘分别列预算。同盘备份不能覆盖整机损坏；给出备份恢复验证需求，不为估算擅自搬迁数据。

### 并发与夜间任务窗口

并发请求、在线用户、模型并行任务是不同指标。外部 API 限额可能先于本地 CPU 成为瓶颈。

使用实测的单 worker 平均任务耗时 t（秒）、任务数 N、窗口 W（秒）和目标占用比例 u（0<u<1），估算 worker 下界：ceil(N × t / (W × u))。说明此式是假设任务独立且近似同质的初估；I/O、资源争用、外部限额和长尾任务会破坏线性扩展，需在候选并发下复测。若 t 已在指定并发下测得，不再重复套线性加速。

本地 ASR 可用实测 RTF（处理时间/音频时长）估算，但录音长度、模型和硬件必须匹配；远端转写需要计入排队、轮询、限流和重试。

发现处理窗口不够时比较：限制前台干扰、优化批次、提高已验证并发、拆分 worker 或更换服务；不能仅建议购买更大机器。

### 网络

考虑峰值同时上传、客户端上行、服务器出口、对象存储/模型服务位置、请求超时和大文件限制。带宽不等于月流量；估算结果需分别列出 Mbps 与每月 GB。

### GPU 与本地推理

只有确认本地执行的组件需要 GPU 时才推荐显卡。核对指定模型/引擎的最新官方模型卡、配置文件及兼容矩阵。

显存需要包括权重、KV Cache（为序列保存的注意力键值缓存）、运行时缓冲和引擎开销。权重的参数量×位宽/8 只是粗略下界；量化元数据、未量化层、专家模型实际驻留权重等不可遗漏。

KV Cache 必须按真实架构、KV 头、层数、精度、实际/最大上下文及并行序列估算；不要把同一个公式无条件套给滑窗、混合注意力等架构。显存容量相同不代表吞吐相同；多卡也未必能无损合并显存。

区分：内存能装下、软件能加载、目标上下文能运行、目标并发满足延迟，四种结论。不能凭理论 TFLOPS 推导承诺的 tokens/s 或首字延迟；只有同条件实测才能用于性能承诺。

## 4. 两个项目的落地重点

### 子曰酒店

根据当前项目确认 SQLite/全文检索/SQL 查询、图片入库和模型 API 实现。没有向量库就不加入 Qdrant 内存账单；没有本地大模型就不推荐推理显卡。

重点测：图片上传/预览/导出的大文件峰值、并发保存和检索、原图增长、备份一致性、档案数量增加后的查询耗时。若新增 OCR、向量化或重排序，再分别估算额外工作进程、模型与索引资源。

### 婚恋 CRM 与录音分析

根据最新需求确认调度时间，历史为 Asia/Shanghai 凌晨 2 点。统计每日录音总时长与长度分布、夜间可用时间、实际转写/分析延迟、API 并发和日限额。

重点测：队列能否在约定时限处理完、夜间任务与白天 CRM 是否争抢内存/数据库、立即处理与批次并发、失败重试及重新分析的额外成本、录音保留期与备份空间。限流引起的积压不能误诊成服务器 CPU 不够。

若两个产品共享服务器，合并预算还要加已有服务、同时构建和备份的峰值；先核实是否共机，不照搬历史部署信息。

## 5. 验证和扩容

优先使用代表性样本在本地或隔离测试环境做并发测试，记录环境、版本、配置、负载、时长、CPU/RAM 峰值、磁盘剩余与 IO、p95 延迟（95% 请求不超过该时长）、错误率、队列积压、任务截止时间完成率。实时 API 测试遵循现有费用和数据授权。

实际生产压测需明确授权、负载上限、停止条件和恢复方案；评估请求不等于购买云资源、跑无限付费请求或压垮线上。无法测时明确“待压测验证”。

扩容条件根据目标设定并说明持续时间：例如队列不能在约定窗口完成、p95 超标且确认是资源瓶颈、出现 OOM（内存不足终止）、剩余磁盘无法覆盖增长与恢复操作。不要给所有项目固定的 CPU 百分比阈值；区分资源不足、慢 SQL、服务商限流和程序泄漏。
