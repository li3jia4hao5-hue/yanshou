# 测试、Agent 评测与验收

## 先确定覆盖范围

将当前需求逐项映射到测试，优先覆盖变更路径、历史失败及高影响数据结果。测试不以数量为目标；不要求每次跑无关大套件。纯展示改动优先截图/交互检查，业务变更增加对应自动化测试。

每个案例记录：编号、需求来源、环境、输入/前置状态、操作、预期、实际、证据、结论。结论只能为通过/失败/阻断/未验证/不适用；不能把阻断算通过。

## 四层证据

1. **代码与构建**：检查差异、类型、构建和相关单元测试。不能由编译成功推断业务可用。
2. **接口与数据**：验证服务端输入、权限、状态流转、幂等性、数据实际保存及重新读取。数据库测试使用隔离副本。
3. **浏览器全流程**：从用户入口执行真实操作，检查页面、请求、持久化与结果。长任务等待明确状态，不把网络一直活跃当失败，也不盲目依赖固定睡眠。浏览器工具不可用则保留未验收项，不绕过工具限制。
4. **Agent 行为**：针对模型输入、检索证据、调用工具和最终业务结果设计案例。区分模拟模型集成测试与真实模型效果测试。

## Agent 评测设计

用少量有代表性的案例先建立基线，涵盖正常、缺失、冲突、失败和越权请求；按项目风险增补，不强制固定数量。

- 精确金额、日期、记录 ID、引用存在性、实际副作用用确定性断言。
- 语义质量用明确评分规则与代表性人工校核；模型评委是辅助证据，不能自己宣布所有业务都正确。
- 调整提示词或模型时保留一组未参与调整的案例。对容易波动的关键任务进行合理重复，记录失败类型，不用一次成功代表稳定。
- 比较同一数据集、工具条件、模型配置和版本；记录任务耗时、调用次数、费用或费用不可得，不伪造精确成本。
- 从“查错资料、未给模型正确上下文、模型误判、工具执行失败、状态保存错误、UI 显示错”中定位失败环节。
- 长上下文案例：插入早期用户限制、后期修正、待完成事项，在压缩/切换阶段后验证保留与最新值；原资料保持可回查。
- 对带副作用的流程，用隔离测试替身验证调用与参数；生产副作用只在当前授权范围内执行。

已采用 MLflow 时复用现有 tracing、数据集和 scorer；否则优先项目测试框架及结构化案例，不引入必需的新平台或收费评委。

## 排错闭环

记录复现步骤与环境 → 收集请求/响应/错误和前后状态 → 提出有依据的根因假设 → 最小验证 → 修复 → 原路径复测 → 相关回归。
新增回归测试应能在修复前失败、修复后通过；在隔离环境验证，避免撤销用户未提交修改。不要通过放宽预期、吞掉异常或使用假数据替换真实失败来“修好”测试。

## 交付判定

- **通过**：本轮约定范围内关键验收均有证据且无阻断缺陷。
- **有限通过**：明确列出适用范围与非关键未测/限制，不能称全面上线就绪。
- **不通过/待验收**：关键流程失败，或关键环节因环境受阻而没有证据。

无权限、浏览器不可用、未配置真实模型等属于验证限制；报告原因和完成条件，不将其描述为已修复的产品 bug。

## 报告模板

根据工作量使用简版或完整表格，不强制小改动生成文档。

```text
项目与版本：
本轮范围及环境：
结论：通过 / 有限通过 / 不通过 / 待验收

需求 | 操作与预期 | 实际结果 | 证据位置 | 状态

问题：严重度、复现步骤、预期与实际、根因、修改、复测证据
未验证：阻碍、影响、完成验证所需条件
上线状态：未部署 / 已部署至明确环境并核对版本
数据与恢复：本轮是否涉及迁移、备份位置与恢复方式（不含凭据）
```

严重度按业务影响解释：数据泄露/丢失、重复收费或主流程不可用优先；视觉细节与局部操作不便分别记录。不要用平均分掩盖关键失败。
